## 公开源码中的具体缺口

固定公开提交：`8e92c892b47f3f934f18ce63da4c4dcb75f0b6bd`。该快照 `backend/cmd/server/VERSION` 为 `0.2.19`；线上 UI 也显示 v0.2.19，但相同版本号不证明提交或二进制相同。

1. `openai_images.go:604` 的 `ForwardImages` 按账号类型分流；OAuth 固定进入 `forwardOpenAIImagesOAuth`，这里没有“自动透传”绕过分支。
2. `openai_images_direct.go:31` 的 `usesCodexDirectImages` 明确枚举 1.5、2、2.5 及 2.5 快照，**没有 2.6 Flare/Sunburst**。
3. `openai_images_responses.go:1812` 的 OAuth 图片转发因此对 2.6 调用 `buildOpenAIImagesResponsesRequest`，目标为 Codex Responses。线上四条实际上游 URL 与此行为一致。
4. `openai_images.go:75` 请求结构，以及 `:247` JSON、`:330` multipart 解析均没有 `Complexity` 字段。
5. `openai_images_responses.go:358` 重建请求，只把已解析字段填到 `tools[].image_generation`，其字段列表没有 `complexity`；原生 Images 构造 `openai_images_direct.go:43` 也缺少该字段。

因此在这份公开源码的 OAuth 路径中，客户端传 `complexity=high` 与不传，会构造出同样缺少图片 `complexity` 的上游请求。仅在客户端改 high 或删字段不能弥补这个缺口。

转换模板 `openai_images_responses.go:384` 的确写了 `reasoning.effort=medium`。**它是控制器推理参数，不等同于图片 `complexity=medium`；目前没有证据证明二者由上游直接映射。** 默认控制器为 `gpt-5.6-luna`，但可被服务器环境变量覆盖，线上实际控制器未核实。

官方 OpenAI documentation 的图片指南写明：2.6 支持 low/medium/high；省略 `complexity` 默认为 high。该文档是公开 API 规范，不能直接证明内部 Codex 端点或此 OAuth 账号具有同样行为和权限。

## 建议修复与验证顺序

1. 先核对线上容器镜像摘要、构建提交和部署时间，确认实际代码；本次没有服务器 shell 或部署配置的证据。
2. 在 JSON 和 multipart 解析、公共图片请求结构、实际出站请求构造中完整支持独立 `complexity`；保留调用者省略字段的语义，校验合法值，避免硬编码成 medium。
3. 核实 Codex 对 2.6 支持的实际接口后更新模型路由。不要仅把名称塞进直调名单，就假定端点可用；也不要只改控制器的 `reasoning.effort`。
4. 在隔离环境检查转换后的脱敏出站 JSON，分别验证 high 与省略字段、generations 与 edits；同时记录实际 URL、控制器模型、图片工具模型及字段是否存在。不要记录认证头、令牌和完整参考图。
5. 修正成功后再进行两模型实图对比。当前累计 10 次请求均无图片，画质评分仍为 N/A。

当前 CPU 约 2.5%、内存约 148/600MB、数据库和 Redis 连接及协程正常；这些瞬时指标不支持“资源耗尽导致本次 400”的判断。后台另有账号 #36 文本 Responses 的 503/重试，与这四次图片参数错误分开处理。
