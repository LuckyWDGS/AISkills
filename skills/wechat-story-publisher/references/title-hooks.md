# 发布标题的钩子

## 把故事名转成读者想点开的标题

工作名用于内部识别；发布标题负责让读者看见一个值得追下去的问题；封面短文案负责在小图上迅速可读。三者可以不同，但必须讲同一个故事。

先用一句话找出最有张力的真实事件，再让标题停在结果揭晓之前。优先用具体人物、动作和反差，不要只写主题词、道理或概括性篇名。

常用切入点按故事选择，不必逐项套模板：

| 切入点 | 读者会想追问什么 | 使用条件 |
|---|---|---|
| 要求与后果 | 照做之后为什么会反转？ | 对方提出的要求和之后的后果都实际发生 |
| 小动作与大反应 | 一件普通小事为什么引发冲突？ | 小动作是推动故事的关键，不是随意放大 |
| 身份或角色反差 | 真正的当事人来了会怎样？ | 角色反差在前段有铺垫，结尾有处理 |
| 具体代价或选择 | 主角会保住什么、放弃什么？ | 金额、期限、所有权等细节有正文依据 |
| 未说完的一句要求 | 这句话后面为什么做不下去了？ | 关键对白和动作足够明确，不能只藏主语装神秘 |

## 小范围候选与选择

通常拟 3–5 个不同角度的候选就够；用户只要一个时，内部比较后直接推荐。按以下顺序筛：

1. **看得懂**：谁做了什么？脱离内部故事代号也能理解。
2. **想追问**：还有一个具体问题未解，而不是已经把结局讲完。
3. **能兑现**：逐项对照正文；找不到依据的价格、动作、身份、情绪结论就删除。
4. **有前段支撑**：前几张能看到标题的核心场景或必要铺垫，不让读者一路等待另一个故事。
5. **简洁适配**：按平台当前实际字数限制检查；读起来顺口，封面截断后仍能理解重点。

轻量记录即可：`推荐标题 / 读者疑问 / 前段依据 / 结尾兑现`。无需制造没有数据支撑的点击率评分。

## 对比示例

仅在对应情节成立时使用这些示例，不能套到不匹配的故事上。

| 平直工作名 | 更具体的发布标题 | 必须有的正文依据 |
|---|---|---|
| 房东让我恢复原样 | 房东让我恢复原样，我照做后她急了 | 房东确实要求恢复；租客确实照做；随后明确出现房东着急或阻止的表现 |
| 房东让我恢复原样 | 退租时我拆了窗帘，房东不让了 | 退租、拆窗帘、阻止都真实发生，窗帘归属清楚 |
| 顾客不是演员 | 售后演到第六遍，真顾客来了 | 有反复排演、准确次数和真实顾客介入；数字不能为了吸引力凭空添加 |

“她急了”仍是情节断言，必须有行为支撑；没有就选更准确的动作。避免“全网炸了”“所有人都哭了”“不看后悔”等无依据话术。不要为了让租房故事更刺激而捏造押金争议、诈骗或金额。

## 标题与制作同步

- 在正式封面和文字导出前选定发布标题；标题变化只重排受影响的文字/封面，画面本身不变时无需重跑全部生图。
- 上传时检查后台标题、封面文字、简介是否相互吻合。发布包名称可保留便于识别的工作名，但应记录最终发布标题。
- 用户说“以后/下次”是后续偏好，不是修改现有线上草稿的指令。
- 复盘点击表现时使用可比曝光、打开率或阅读指标，记录日期和口径。标题更有吸引力是编辑判断，不能据此宣称已经提高点击率。
