# VPS 自用节点搭建与排障

把用户自有服务器交付为可导入、可测速、可联网、可维护的节点。使用用户当前选择的客户端和协议；已有服务能用时优先局部修复。默认中文沟通。

## 开始时确定范围

- 先读取当前项目交接和已有部署信息，再检查现场。已有授权和用户选择继续有效，不重复要求确认。
- “解释这条提示”“先不修改”只做解释和必要只读检查。创建或更新本技能不意味着重新部署当前 VPS。
- 新搭建只补齐真正缺失的信息：服务器地址、SSH 端口/用户和密钥文件、客户端、域名可用性；需要流量展示时再确认额度单位、计费方向、重置日/时区。询问期间继续不依赖答案的检查。
- 不把旧案例的 IP、密钥、订阅地址、网卡索引、服务 PID、SNI、端口和配额当成新任务参数。不从示例创造真实凭据。
- 将任务私密配置留在该项目受限目录；技能自身只保留方法和脱敏案例。

## 必须保留的验证逻辑

1. **先证明路径。** 新开一个 Mihomo 进程不等于直连：其出站仍可能经过用户原有 TUN。测试核心必须绑定实际物理网卡，检查节点级覆盖和 dialer-proxy，记录到 VPS 的实际路由/连接证据。物理绑定只排除本机 TUN，不能排除上游路由器代理或多线路。
2. **使用最终成品。** 下载最终发布的订阅进行语法和联网验证；手写测试节点的成功不能代替订阅交付成功。解析 YAML 后覆写测试参数，不靠拼接重复顶级字段。
3. **分层下结论。** TCP 通、REALITY 通、网页通、DNS 通、客户端实际使用通是不同层级。出口 IP 相符也不能单独排除“旧代理 → 新 VPS”的链路。
4. **保护用户现有网络。** 先做隔离测试。用户授权导入/修复客户端后，记下原订阅和代理选择再切换；新订阅断网时先恢复原选择。只停止本任务启动且身份已核实的进程。
5. **版本以现场为准。** 核对客户端实际核心版本与服务端版本，再看官方兼容性说明和变更记录。不要盲目升级、降级或永久固定某个 REALITY 指纹/SNI。
6. **不为检测分数改配置。** `resolver_count=0` 只是测试未观察到解析器；fake-ip 是受支持的 DNS 模式。网络正常时，不能仅因“DNS 黑洞/致命”标签就禁用 TUN、更换 DNS 或承诺能避开平台识别。
7. **一次只验证一个改动。** 有 DNS 证据时先修对应上游；仍失败再按授权比较 BBR 或其他变量。吞吐、网页成功率和时延分别报告；一次通过或小样本差异都不能证明长期修复或唯一根因。

## 可复用检查脚本

[scripts/probe_proxy.py](scripts/probe_proxy.py) 使用本机显式 HTTP 代理连续发起小请求，校验 HTTP 状态和预期出口 IP，输出脱敏 JSON。只需要 Python 标准库和 curl；不修改客户端、不启动/停止核心、不设置系统代理。

```powershell
python scripts/probe_proxy.py --proxy http://127.0.0.1:17890 --expected-exit-ip 203.0.113.10 --attempts 10 --output work/proxy-check.json
```

这里的 IP 和端口都是示例，执行前替换为已核实的目标和隔离测试端口。工作目录为技能目录时上例脚本路径才成立；其他目录使用脚本绝对路径。报告中的 `proxy_http_passed` 仅表示这一层通过，物理路径、DNS、TUN 和用户客户端验证仍须单独记录。

## 完成条件与交付

- 服务运行、配置持久化；服务端配置、最终订阅、客户端实际加载参数一致。
- HTTPS 验证链和主机/IP 身份成功，订阅返回正确格式；不要用忽略证书错误作为验收。
- 根据本次任务验证相应层级；新部署交付包含独立测试、原客户端、延迟、小请求、出口和 DNS。维护局部配置无需重跑全部部署验收。保留失败样本，区分“授权改动完成”和“全部故障已消除”。
- 在用户授权范围内刷新/导入并验证实际客户端。若未做，明确写“客户端未验证”；用户说“目前可上网”记为用户确认，不捏造自动测试结果或具体出口。
- 核对流量计数来源、单位和重置规则；证书续期任务和 reload 链路可用。实际未来续期尚未发生时不要声称已经验证过。
- 提供私有订阅文件、受限管理信息、简短使用/续期/回滚说明及脱敏结果。明确订阅端口与代理端口的用途。
- 清理本任务临时转发规则和临时进程；保留用户现有代理及授权内的运行配置。更新当前项目交接。

若一次修改后出现新的断网或配置校验失败，回滚该次修改再分析。相同假设连续两次失败后检查证据和版本，避免继续堆叠变更。
