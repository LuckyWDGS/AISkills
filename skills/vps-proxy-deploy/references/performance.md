# BBR 开启与国内性能对比

## 先区分问题

BBR 是 TCP 拥塞控制；REALITY 是代理传输的安全与握手机制。授权开启 BBR 不等于授权关闭 REALITY、改 SNI/端口或 DNS。BBR 可能改善某条线路的吞吐和排队延迟，不能缩短跨洲传播距离；下载、上传、空载 RTT、负载 RTT 要分别判断。

## 幂等启用与验收

- 读取当前内核、`tcp_congestion_control`、`tcp_available_congestion_control`、模块支持、实际 qdisc 和持久配置。已启用且持久化正确时只核验，不反复关开。已有内核支持时无需为此升级内核或重启机器。
- 确有缺项时，备份原算法和相关文件；按该发行版机制加载现有模块、设置默认算法并持久化。核对 sysctl 配置优先级，避免重复/冲突文件。保留现有 qdisc，只有版本要求或明确证据支持时才单独调整。
- 验证新建 TCP socket 的 `getsockopt(TCP_CONGESTION)`；再用 `ss -tinp` 或等效工具核实代理服务实际已建立连接的算法。系统默认值、新 socket、已有 listener、已建立连接是不同证据。Linux 文档说明被动连接可继承 listener 的选择；不要只看到 sysctl 为 BBR 就断言所有服务连接已切换，也不要只看到旧 listener 的算法就断言新连接没有使用 BBR。[Linux TCP sysctl](https://docs.kernel.org/networking/ip-sysctl.html)
- 不为让旧连接立刻换算法而批量断开连接或重启代理；若实际目标连接仍使用原算法，先核对程序的 socket 设置与内核行为，再提出范围最小的处理。
- 对比服务 PID、代理/DNS/订阅配置哈希、qdisc；用小请求验收联网。持久文件正确和“重启后实际验证”分开记录。回滚仅撤销本任务创建且内容未被后续修改的文件，恢复记录的原算法。

需要启用时，运行时设置为 `net.ipv4.tcp_congestion_control=bbr`；在已审查冲突与加载顺序后，用独立 `/etc/sysctl.d/` 文件持久化。模块化内核可用 `/etc/modules-load.d/` 加载已有 `tcp_bbr`；内建实现不要求另写模块文件。命令成功后仍要做上述新 socket 与代理连接检查。已开启且持久化正确时直接报告核验结果，避免重复修改；不把内核自带 BBR 宣称为安装了 BBRv3。

## YABS 能说明什么

YABS 网络测试测量 VPS 与所列公共测试点之间的链路。即使某个测试点位于亚洲，也不等于用户在中国境内访问该 VPS 的表现。按[官方脚本](https://github.com/masonr/yet-another-bench-script)当时版本核对参数；例如 `-f/-d` 跳过磁盘、`-g` 跳过 Geekbench，并没有关闭网络测速。

用户已授权测速时继续执行。未明确包含大流量测试时，先说明预计流量和短暂带宽占用，再确认范围。先下载检查官方脚本、记录版本/哈希并设置时限，不把商家粘贴的 `curl | bash` 当作无需审查的命令。记录 RX/TX 增量时注明它包括测试期间其他业务，不能伪称精确测试计费量。

## 中国境内 A/B 测试

1. 确定测量方向和路径：国内客户端所在运营商/地区、物理网卡到目标 VPS、是否含代理协议。按[路径验证](validation.md)排除本机旧 TUN 接力，单独核实上游路由器代理/多 WAN；无法排除时明确标为“当前实际接入路径”，不能称作纯国内宽带直达。VPS 到国内网站和国内客户端到 VPS 也不能互相替代。
2. 固定端点、协议、连接数、传输大小/时长和其他变量，交错进行多轮 CUBIC/BBR 测试。尽可能使用新的测试连接；若复用连接切换算法，记录连接状态残留、暖机和顺序偏差。每阶段实际读取 socket 算法。
3. 可在隔离测试进程中按 socket 选择算法，避免反复改生产默认值。测上传时，服务器的拥塞算法不能代替国内发送端的算法；对每个方向说明哪个发送端发生了变化。
4. 分别记录下载/上传速率、空载 RTT、负载 RTT、超时/失败、样本范围与中位数，单位写 Mbps 或 MB/s。小样本和单条线路不能代表全国，也不能把原始 TCP 测速当成 REALITY 端到端速率。
5. 临时监听/转发尽量限来源和时间，预先记录精确撤销动作。测试结束核对临时进程/端口/防火墙规则已清理，生产配置和服务仍正常。失败样本保留，说明是否纳入汇总及理由。

交付应回答“在哪条线路、哪个方向、有多大改善、哪些指标没改善、依据有什么限制”，不要承诺普遍降低延迟。

## 网页超时的 BBR 单变量比较

- “开启后才觉得不稳定”是需要验证的时间关联；原始 TCP 或 YABS 吞吐结果不能代替真实代理网页成功率。若有对应 DNS 错误，先按 [DNS 修复](dns-repair.md)定位并验证，仍有超时才在授权范围内比较 BBR。
- 固定 DNS、规则、代理协议、端点、TLS 校验、超时阈值和请求方式，交错进行 BBR/CUBIC 多轮小请求。分别记录域名访问与固定目的 IP 访问（保留正确 SNI/Host）；预先限定次数和时长，保留失败，不反复测试到全部通过。
- 优先隔离测试，但只有同一实际代理路径的请求才能回答用户的网页体验。若需临时改变系统默认值，说明会影响同期其他新 TCP 连接；保存持久配置哈希，并在切换前设置可独立执行的定时恢复，再用 `finally` 主动恢复。不要为短暂比较改开机配置、qdisc 或重启代理。恢复后取消定时任务并检查采样进程已结束。
- 每阶段验证 sysctl、新 socket、代理新建连接的算法。以新 inode、连接四元组或受控测试标记区分旧连接；只采样到全服务新连接时应说明包含后台业务，不能声称每个请求都逐一对应。已有连接可继续使用旧算法，不批量关闭它们；若请求复用连接则单独说明。
- TLS EOF、约固定秒数失败只是症状；必须结合核心/服务器日志区分 TCP、REALITY 握手、解析与目标 TLS。无失败抓包时不能下定论是端口封锁、BBR、SNI 或路由器。
- 报告各轮成功/总数、失败类型、成功请求耗时；连接建立+TLS+HTTP 总耗时不能写成 ping RTT。小样本中关闭 BBR 没改善，支持保留既有设置；不能据此量化普遍稳定性收益或排除 BBR 的任何可能影响。无明确证据时恢复测试前配置，保留未解问题。
