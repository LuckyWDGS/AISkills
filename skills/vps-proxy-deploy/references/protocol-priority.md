# 协议优先级与实测速率

## 本用户的长连接偏好

用户看重长期保密、CLI 长任务稳定和少切换。在三个协议都已验收、使用同一 VPS 出口的前提下，采用 Mihomo 原生 fallback，候选顺序为 **VLESS Vision / REALITY → AnyTLS → Hysteria2 Gecko**。此顺序反映用户当前偏好，其他用户、线路或缺少协议的主机要按实际情况选择。

- REALITY 主用。对支持的 Mihomo，在该节点的 `reality-opts` 下启用 `support-x25519mlkem768`。用冷连接同时核对实际 ServerHello 选择、REALITY 认证、HTTPS 成功和预期出口，再使用“混合握手”标签。单凭目标网站支持该组或 YAML 开关，不能证明协商成功。外层握手记录所能证明的范围限于该次握手，Vision 的业务数据路径需要单独判断。
- AnyTLS 为第一备用。实测其证书身份、认证和访问。TLS 版本、某次选中的密钥交换组、服务端是否拒绝传统组是三个独立事实。若考虑调为主用，在同一路线的几个晚高峰，用中立端点观察持续连接的中断次数、重连和请求失败，同时记录观察时长。响应更快且长连接表现相当时，可提到第一位。
- Hysteria2 Gecko 为第二备用，保留在可用 UDP 上工作的独立传输方式。测实际认证和数据收发，保留客户端核心连接 VPS 所需的 UDP。三条协议共享主机和出口 IP，IP 或整机失联会同时影响它们。

优先顺序写在 `type: fallback` 组的 `proxies` 列表。保留经核验的健康检查和保护组，记录是否有手动固定。主用恢复后，新连接可能较快回切。既有流式任务的中断与应用重试另测。该用户选择保留原生行为。

## 把顺序迁移到另一台服务器

先读目标机当前发布的 HTTPS 订阅、运行服务和同机业务。按节点类型、Vision flow 和认证参数定位成员，保留目标机自己的凭据、证书、端口、SNI、分流、计费及订阅 URL。用该机的真实客户端连接验证候选，再更新组顺序。仅更新订阅时，保存可回退的旧正文，按旧摘要检查并原子替换，保留文件权限。重新下载公开入口，核对字节、响应头与配置差异，再验证新主用和两级备用。

故障验收优先在关闭 TUN、绑定实测物理网卡的隔离客户端里使指定候选失联，观察实际新连接选路。同出口必须逐协议核对。全组失联时请求应失败，恢复时应重新经代理成功。分别注明模拟故障、真实服务状态和未覆盖的长期观察窗口。

## 防火墙变更后的测速

用同一测点、请求大小与客户端，交错测下载、上传和新建 HTTPS 的首字节时间。记录单位、有效字节、失败样本、出口和实际选中的节点。比较按路径生效的物理网卡阻断时，直接运行被保护的可执行文件，核对活动规则与 TUN 或回环代理连接链。保留现有保护，可同时使用原先已有相同规则的旧版本，以及使用相同网络库的独立宿主作对照。两者都与同程序、同条件的防火墙开关实验有区别。公网跨时段的差额也不能单独确定因果。

### 一次以太网实测

同一 VPS、同一 Cloudflare 测点，每个协议三轮，每次传输 8 MiB。下表是当次中位数，反映短请求和端到端传输，供复测时了解指标含义。

| 链路 | 下载 Mbps | 上传 Mbps | 新 HTTPS 连接首字节 |
| --- | ---: | ---: | ---: |
| REALITY | 8.15 | 14.71 | 1,194 ms |
| AnyTLS | 23.89 | 14.52 | 561 ms |
| Hysteria2 Gecko | 45.41 | 25.09 | 569 ms |

同期为三个 Windows 运行时程序补上物理网卡出站阻断。新旧 Node.js 七组双方成功的配对中，新版上传全部较慢，中位数为 8.7 对 10.0 Mbps。另有一组仅新版失败。两版程序版本不同，物理接口规则范围相同。使用同一 WinHTTP 库的两个 PowerShell 宿主做六组对照，上传、下载均各有三组受保护者较快、三组较慢。HY2 本次下载和上传的中位数较另一个时段的历史记录分别低 16.1% 和 15.6%。记录观察到的 Node.js 差异，保留其归因的不确定性，在其他 VPS 上另行测速。

另一台 VPS 每个协议交错测三轮，每次传输 4 MiB。REALITY、AnyTLS、HY2 的下载中位数分别为 6.64、10.33、26.13 Mbps，上传分别为 7.79、11.18、11.70 Mbps。三个协议均通过约 22 秒的连接复用测试。跨晚高峰的长期稳定性仍待观察。
