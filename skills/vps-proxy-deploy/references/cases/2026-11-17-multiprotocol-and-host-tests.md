## 本机经验

- 实际发现的独立 CLI、安装树 EXE、更新程序及 SSH 路径纳入物理接口保护；保留回环、TUN 和核心 HY2 UDP。路径扫描以高权限任务维护，普通用户不能改脚本；轮询仍有首次启动竞态。
- 应用静态 HTTP(S) 入口只指向回环强制代理，NO_PROXY 限回环；未运行 Claude 或 Claude Code。WSL/容器未取得等价保护证据，既有业务容器未重建。
- 物理接口 IPv6 绑定关闭，另有公网/转换前缀保护；保留 ::1。国内明确 DIRECT 不变，无 CN/IP 兜底；WebRTC 策略未改，保持 `default_public_interface_only`。
- GUI 基础配置曾覆盖脚本/订阅 TUN。最终以运行时核对各持久来源，不把生成文件作为唯一维护点。
- `strict-route:true` 时，同一临时服务/程序的 ::1 请求返回 WSA10013；改为 false 后返回 204。最终各持久来源一致，并保留 TCP53 劫持与防火墙。该 A/B 只解释此环境的回环回归，未启动 UE，不能说旧 DDC 故障已解决。

## 故障与恢复

独立本地恢复看门狗先验证；实际 Chrome、无代理环境的受保护 Node/Python/PowerShell、数字 IP TLS、国内外 STUN（域名与数字 IP）、DataChannel 和本机回环参与检查。

最终九阶段为：基线 → 上游503 → 恢复 → 入口/TUN关闭 → 恢复 → 真实核心服务停止 → 恢复 → 物理网卡禁用 → 恢复。真实停核窗口约 6.24 秒，物理断网约 6.54 秒；故障时受测新连接失败且未观察到直连公网候选，正常/恢复时出现预期代理出口，DataChannel 双向成功，国内控制请求命中 DIRECT。

保留的失败包括：早期 HY2 请求超时、REALITY 短连接结束后路径采样缺失、重载后一次订阅下载失败、早期恢复时域名 STUN 701/DataChannel 延迟。最终一轮也有早期恢复采样未通过，有限重试后通过；它的具体失败项不由早期轮次推断，不能称全部立即恢复或抹去首次失败。

最后发布差异仅为 `tun.strict-route`，节点参数及 DNS/rules 保持；回环修复后重新验证故障矩阵。临时进程/端口清理、正式核心/网卡恢复均有记录。
