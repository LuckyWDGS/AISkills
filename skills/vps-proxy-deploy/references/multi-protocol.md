# 同出口多协议与连接切换

用于 HY2、AnyTLS、VLESS Vision/REALITY 等组合的部署和切换诊断。先完成[服务端与最终订阅验收](validation.md)，再按[本机阶段约定](local-review-and-approval.md)处理正式客户端。历史兼容组合不是未来版本的安装锁定。

用户重视长期保密和长连接稳定时，如何在三个已部署协议间排序，以及如何把顺序应用到另一台机器，见[协议优先级与实测速率](protocol-priority.md)。

## 协议解决的层次

- HY2 的客户端到 VPS 外层采用 QUIC/UDP，TCP 型方案使用 TCP。应用的 HTTPS 仍在隧道中；Claude 等对端通常不能仅从应用请求直接知道本机到 VPS 用了哪种外层代理协议。不同实现的重连、复用和拥塞仍会改变应用体验。
- TCP 可能在限制 UDP 的网络更可靠；HY2 可能在有丢包的路径表现更好。没有“TCP 永远更安全”或“UDP 必然增加 AI 负担”的结论，以实测握手、流式请求、丢包和负载时延决定主用。
- Linux BBR 是内核 TCP 拥塞控制，不是 HY2 的用户态 QUIC 控制。带宽参数按实际容量及该版本文档选择，不填超过可用容量的数字来“提速”。
- 同 VPS、同出口需分别用各协议确认；组名、相同 server 字段或一个查 IP 请求不够。协议共享 IP、主机、带宽与上游，不能消除共同故障，也不能保证长期不被屏蔽或服务账号不受限制。

## 组合配置检查

1. 逐条核查客户端/服务端真实版本及互通。TCP 与 UDP 可使用相同数字端口，但两个普通 TCP 服务不能同时占用同一地址/端口；订阅 HTTPS 和管理入口另行规划。
2. AnyTLS/HY2 校验证书链与域名或 IP SAN；REALITY 核对目标、SNI、公钥、short ID、指纹及 Vision 参数。按用户限制排除 SNI，其他目标从 VPS 和客户端分别测试；不要取消证书校验排障。
3. fallback 只收录已验收的代理，嵌套组也不含 DIRECT。HTTP 健康检查成功不代表 UDP、DNS、全部目标或长连接正常；每个候选能力分别测。
4. 保留核心自身到 VPS 的必要 UDP，同时对受保护应用采用[UDP 拒绝回退及物理接口保护](traffic-privacy.md)。TLS 内承载业务 UDP 与外层采用 UDP 是两个概念，按实现实测。
5. 记录各协议正常/失败/恢复时的实际出口；多个端口与一个固定出口不能代替[独立入口容灾](filtering-and-transports.md)。

## Mihomo fallback 的实际语义

以下结论核对过 Mihomo **v1.19.33**；后续按运行版本读源码与文档：

| 设置或状态 | 含义与局限 |
| --- | --- |
| 候选顺序 | 未被手动固定时，优先第一个健康候选；不是按最低延迟挑选 |
| `interval` | 定期健康检查间隔，不是定时换协议；例如每 60 秒检查不代表每 60 秒切换 |
| `timeout`、`lazy` | 分别影响检查超时与空闲时检查行为；应结合运行时历史核实 |
| `max-failed-times` | 某些连接拨号失败触发额外健康检查的门槛；不是“连续几次探测失败才切换”，也不是冷却/回切延迟；特定错误可立即触发检查 |
| 主用恢复 | 更靠前候选重新健康后，新连接可能很快回到它；不可把配置描述为已连续稳定数分钟后才回切 |
| 手动固定/控制 API | 查询当前组类型、选择、固定状态与能力；不能假定所有组和版本都与 select 相同，也不能笼统说 fallback 完全无法手动选择 |

源码：[fallback.go](https://github.com/MetaCubeX/mihomo/blob/v1.19.33/adapter/outboundgroup/fallback.go)、[groupbase.go](https://github.com/MetaCubeX/mihomo/blob/v1.19.33/adapter/outboundgroup/groupbase.go)、[healthcheck.go](https://github.com/MetaCubeX/mihomo/blob/v1.19.33/adapter/provider/healthcheck.go)。

## 频繁切换的实际影响

既有 TCP/QUIC/代理连接不会跨协议无缝迁移。旧连接可能继续走原链路，新连接使用新候选；原链路断开时，流式输出、WebSocket、上传或长任务可能中断，应用是否恢复取决于自身重试。重试还可能造成请求重复，不能替应用保证一次性执行。

Clash Verge Rev **v2.5.10** 的手动选节点路径在启用 `auto_close_connection` 时会按旧代理链关闭相关连接；核心自动 fallback 不经过同一 GUI 选择逻辑。要分别观察“手动切换主动断连”和“旧通道故障造成断连”，不能把手动操作的行为直接套到自动切换。参考[该版本选择逻辑](https://github.com/clash-verge-rev/clash-verge-rev/blob/v2.5.10/src/hooks/use-proxy-selection.ts)。

稳定主用、真实故障才切备用通常更适合长会话；不为几毫秒差异频繁手动切换。若需要延迟回切或连续健康窗口，先确认当前核心真正支持的机制；没有则明确“待设计/未实现”，不要编造 `cooldown` 等字段，增大检查间隔也不等于迟滞。额外控制器/脚本会增加维护和本机变更，须先提出具体方案。

固定出口只减少出口变化这一变量，不能承诺避免平台检测；恢复时的重连和请求失败仍可能被应用观察到。未运行真实业务时只报告网络层结果。

## 隔离验收与记录

- 使用最终订阅副本，逐协议验证 HTTPS/204、出口、所需 UDP DNS/STUN 与核心 DoH；绑定实际物理接口并排除旧 TUN 接力。
- 验证“第一候选坏 → 第二”“前两候选坏 → 第三”“全部坏 → 请求失败”；改错测试端口只是客户端故障模拟，不是已停真实 VPS。
- 主用恢复时记录检查时间、选中候选、新旧连接及重连；用受控流式/长连接探测评估影响。用户禁止测试的 AI 服务不能用作探针。
- 身份负例保持 TLS 验证：错误 SNI 的 x509 失败支持身份校验生效；无效 REALITY 公钥被密码库拒绝只证明该负例失败，不是完整中间人攻击验证。
- 保留原始失败、恢复等待及有限重试；短请求全部成功不等于持续带宽、长会话或长期抗干扰验收。后续字段变动需做最终订阅差异检查和相应层级复测。
