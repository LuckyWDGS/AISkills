# 出口保护的故障与恢复测试

只在用户请求严格失效/断网测试时执行干扰性阶段；普通规则检查使用只读核对和隔离探测。技能更新不执行这些操作。目标是证明指定应用、协议和观察窗口内的行为，不是保证平台不会判断地区或所有网络永远无泄漏。

新部署先完成服务器和隔离订阅测试，本机测试按[检查、报告、明确授权](local-review-and-approval.md)进入。已经获准的具体测试不重复询问；禁止访问的服务不用作探针。

## 先使恢复可执行

1. 保存当前订阅、组选择、合并配置和持久来源哈希、TUN/监听、物理网卡身份与启用状态、程序/核心身份、防火墙相关规则及浏览器有效策略。含凭据的备份放受限目录，不进入技能或仓库。
2. 使用有界请求、短故障窗口及本地结果文件。先验证恢复方法，再启动独立恢复看门狗；它需要能在主测试进程或代理通信中断时工作，身份/权限和入口不能依赖即将关闭的网络。不要仅靠同一进程的 finally。
3. 一次只注入一类故障；恢复通过后才开始下一阶段。主流程 finally 恢复，看门狗在期限届满或主进程结束时恢复。若不能建立恢复能力，先完成无干扰测试并说明未测项，不把准备失败算作故障测试通过。
4. 还原每张网卡的原启用状态，保留原本禁用的设备；选定节点/订阅及持久文件若已被用户修改，停止旧快照覆盖，按最新配置恢复。不要为结束测试关闭所有用户连接。
5. 故障注入前核对当前组类型、手动固定状态及控制 API 的实际能力/响应；恢复包含解除测试固定与恢复原选择。不要假设 fallback 与 select 完全相同，也不要把一次选择 API 失败记成故障节点已生效。

## 最终配置下的九阶段矩阵

| 阶段 | 操作 | 受保护流量预期 |
| --- | --- | --- |
| 1 正常基线 | 当前可用节点和 TUN | 成功并取得已确认的代理出口 |
| 2 上游故障 | 受控本机故障代理，例如 HTTP 503 且不支持 UDP；临时配置 | 请求失败；WebRTC/原生 STUN 不取得直连公网地址 |
| 3 恢复上游 | 移除临时故障节点、恢复原组选择 | 再次正常代理出口 |
| 4 入口/TUN 关闭 | 临时关闭代理监听与 TUN，保留可恢复的核心控制通道 | 不依赖代理环境变量的受保护程序也应失败 |
| 5 恢复入口/TUN | 恢复各监听、模式和路由 | 恢复正常代理出口 |
| 6 真实停核 | 按授权停止实际核心/服务，验证旧核心消失且相关代理监听不存在 | 无环境代理的受保护新连接也失败，无直连公网候选 |
| 7 恢复核心 | 恢复服务、核心、选中配置与各监听，核对新的进程身份 | 预期出口、DNS、浏览器和回环恢复 |
| 8 物理断网 | 按授权短时禁用实际物理出口，记录 Disabled | 请求失败，无可用公网候选 |
| 9 恢复网卡 | 恢复原启用状态与路由 | 再次正常代理出口 |

HTTP 503 节点是可控模拟，不等于关闭真实 VPS；监听/TUN 关闭不等于停核；“TUN 关闭”不等于物理网卡断网。真实停核阶段在整个故障窗口检查服务状态、核心身份及监听，防止服务管理器自动拉起而测试了另一种状态。正常停止服务也不等于模拟所有崩溃方式。重启机器、切网和新的公网 IPv6 环境单列，未获准阶段写未测试，不用其他阶段替代。没有实际全球 IPv6 连通性时写明“公网 IPv6 未实测”。

## 恢复不能只看 HTTPS

恢复可先出现 HTTPS/数字 IP STUN 成功，随后才恢复域名 STUN 或 DataChannel。提前限定恢复的总等待窗口、采样次数和判定项；逐次保留失败、错误码与时间，全部必需项恢复后才进入下一阶段。超过界限则恢复原配置并报告失败，不无限重试直到“全绿”。

曾观察到 Chrome 域名 STUN 错误 701、数字 IP 已可用，稍后域名与 DataChannel 才恢复；这不是立即恢复，也不能只凭 701 归因为公网泄漏。既要检查有无意外出口，也要检查应当可用的基线/恢复探测是否完成。

## 每阶段的有区分力的探测

- 显式专用代理入口：HTTPS 出口查询；记录接口、监听进程、选择组和响应出口。
- 原生网络：Python 等受保护程序对经核实的国内/国外 STUN 数字 IP 发 UDP，数字 IP TCP/TLS 保留正确 SNI 与证书验证。
- 无代理环境变量的受保护 CLI：分别请求国内/国外受控查 IP 服务，验证 TUN/防火墙层，而非只证明 HTTP_PROXY 生效。
- 实际浏览器 WebRTC：国内/国外 STUN、域名/数字 IP、收集完成和错误状态；启用代理 UDP 模式要求基线/恢复成功，限制模式另按用户预期验收。
- 正常及恢复时保留国内网页控制：抖音/B站/公众号等明确目标的新连接仍命中 DIRECT，并有响应数据；名单外普通 HTTPS 命中默认代理，不添加检测站特例。
- 本机控制：localhost、127.0.0.1、::1 的可用服务仍可访问；这不是公网直连例外。异常先按[回环排障](loopback.md)分层，避免加固破坏开发工具。

关联唯一测试路径/源端口、目标、发起进程、核心规则、实际出口和时间；TLS 嗅探完成后再取连接元数据。可控服务日志/接口证据支持路径判断。浏览器 opaque 响应不是可读 HTTP 200，HTTP 403/404 也不能直接归类路由失败。

故障时“无候选/请求失败”只有在探测确实执行、服务器基线有效、阶段状态已确认且恢复再次通过时才有意义。CLI 没有 WebRTC API，但能通过 UDP/STUN、HTTP/HTTPS、DNS 或子进程进行联网；两类通道都要覆盖。DNS 解析链单独记录，不能由出口 IP 一致推导。

## 收尾与结论

- 在最后一次规则变更后运行相应矩阵；旧版本通过不能验收随后修改的配置。保留修复前的泄漏样本、准备失败和附加连通性失败，不用成功样本覆盖。
- 核对持久哈希、当前订阅/选择、TUN、监听、有效防火墙规则与配置文件，以及网卡恢复状态。只终止身份核实为本任务创建的测试进程，释放临时端口，移除临时节点并确认看门狗退出。
- Chrome 实测不代表 Edge 实测；受控 Node/Python 测试不代表运行过 Claude Code、插件或全部应用。明确是否测试登录、TURN、中继、真实音视频、重启及切网。
- 分层记录“自动实测通过、用户确认、未验证、失败”。备份从首次变更前开始，后续每层保存 before/after；按逆序撤销且校验当前哈希，不能把已经改过的最新快照当最初基线。

## 已有案例的证据边界

2026-11-15 的记录包含一次“不支持 UDP 时原生 STUN 返回直连出口”的失败；增加进程 UDP 拒绝和末尾拒绝后复测通过。后来用户启用 WebRTC，当时完成七阶段，未包含真实停核。2026-11-17 的[三协议与主机案例](cases/2026-11-17-multiprotocol-and-host-tests.md)补做了真实停核，回环修复后完成最终九阶段；含早期恢复失败及有限重试，不能称全部即时通过。

实际 Chrome 的受测 STUN 只返回预期代理地址，DataChannel 双向收发成功；故障阶段没有公网候选。Edge、真实 Claude 会话、TURN/TLS、公网 IPv6、WSL/容器和开机/切网未取得同等实测证据。该案例说明需要验证最终配置，不提供永久安全保证；节点 IP、规则数、程序路径和网卡名不能复制为新现场参数。
