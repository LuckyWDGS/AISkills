# 第一人称室内关卡的通行与性能验收

窄过道、转角柜和带孔台面既有可见表面，也有角色移动使用的碰撞形状。在编辑器里向前
走一小段，只覆盖起步。要交付可玩的室内关卡，先在图上标出入口、工作区、转身区和返
回路线，再从真实 PlayerStart 用项目角色走完。

## 用项目输入走完整条路线

1. 从已摆放组件的世界范围确定站位，给胶囊留出半径。把“到水槽”拆成走到水槽柜前、
   继续按向前、柜体阻挡、转向、离开。记录目标物，防止角色被另一处碰撞提前挡住也
   算到达。
2. PIE 从当前游戏 world 读 Pawn、控制器、胶囊尺寸和落地状态。Development 独立包
   可用带显式参数的测试驱动调用 Enhanced Input 的 `Input.+key`、`Input.-key`。从
   当前项目的 IMC 确认实际键名，厨房案例使用 `Gamepad_Left2D` 移动和 `Mouse2D`
   转向。二维值形如 `Input.+key Gamepad_Left2D X=0 Y=0.55`。按真实位置和朝向切换
   步骤，给加速、刹停和按键释放留出 tick。使用独立 profile 和后台游戏窗口。
   [Development 包输入与退出](game-production.md#后台独立包的输入存档与退出证据)
3. 在每个检查点记录坐标、yaw、是否落地、是否仍由原控制器控制。沿路径留取中间样
   本。在柜前继续输入，观察速度降至接近零，再用定向射线读出柜体网格和距离。在终
   点同时检查返回入口、真实引擎退出码和运行时错误。
4. 遇到角色卡住，保留最后的输入、位置和阻挡法线。按角色通道 `ECC_Pawn` 和实际胶
   囊做短距离 `SweepSingleByChannel`，输出命中的 Actor、网格和距离。诊断时将胶囊
   略缩，避免起点直接重叠地板。Visibility 射线仍用于确认台面、孔与可见表面。

厨房原图中，一条视线沿过道无遮挡，第一人称角色也从入口移动了约 68 cm。独立包实际
走向炉台时，半径 34 cm 的角色停在约 `(65, 50)`。向 +X 和 +Y 的短胶囊探测都在
2.19 cm 命中同一块石材挡水条，法线约为 `(−0.71, −0.71, 0)`。三段细长饰条合并导入
后的简单凸壳跨过了通道。只对该组件临时放行 Pawn 后，角色才能走到两处真实柜前。这
样的单变量实验用于定位责任网格。

## 修复复合形状

静态的 L 形镶边、U 形挡水条和门框可按实物段拆成多个简单碰撞体。确需使用准确表面
且几何量小的固定摆件，可在候选目录复制 StaticMesh，通过
`StaticMeshToolset.SetCollisionComplexity` 设置 `CTF_UseComplexAsSimple`，再将候
选关卡的组件指向副本。读回碰撞复杂度、实际材质槽、组件对 Pawn/Visibility 的响应
和物理开关。复杂三角碰撞还需结合具体网格的运动方式和成本评估。

在实体饰条上做应命中的简单查询，再在围出的空区做应穿过的查询。沿原输入路线压向炉
台柜和水槽柜，检查两处实体仍阻挡角色。若有灰模和精装两张图，把修复用于两处真正引
用该构件的组件，保存、重载，并针对最终地图 cook 和启动。

UE 5.9 Preview 的厨房候选对 900 个三角面的静态饰条使用了这一办法。在 Windows
Development 包内，三处垂直简单查询均在 94.2 cm 高处命中，围出的过道空区没有命
中。该组件对 Pawn 与 Visibility 仍为 Block。角色在约 `(96, 106)` 和 `(241, 81)`
分别接触炉台柜与水槽柜，转身约 180° 后沿台边返回。两处可见柜面距胶囊中心约 38.4
cm，胶囊半径 34 cm。在这个案例中，距离由简单移动碰撞与可见柜面之间的小偏移决定。

## 同一路线测 CPU 与 GPU

- 明确包构建、RHI/Feature Level、实际后缓冲尺寸、画质、屏幕百分比、VSync、限帧和
  其他正在渲染的进程。先跑一次原路线预热，正式时段由同一个状态机驱动。NullRHI 可
  以复现输入与物理，用硬件 RHI 采集 GPU。
- 官方 `Agent.PerfCapture <秒数> <名称>` 会生成 `Saved/Agent/<名称>.perf.json`，
  含帧间隔、Game、Render、GPU 的 avg/p50/p95/p99/max 和上下文。`Agent.Capture`
  会暂时冻结世界并引入截图开销。若路线长短随实际帧率改变，固定秒数可能只覆盖半
  圈。另在预热结束、返回入口的两个真实事件间记录每帧，保存样本数与路线时长。GT、
  RT 和 GPU 可能并行，不要相加。
- 判断植被成本时，记录具体组件、LOD 数、可见性与碰撞。对照相同路径、画面及设置，
  交替运行多个独立进程。仅隐藏指定植被估计其整体可见性影响，还包含阴影和遮挡变
  化。要量化某一级 LOD，必须 cook 该 LOD、在目标距离核实实际选择，并在同样条件下
  重新采样。p95 或 p99 的单次差异要与重复运行的波动一起报告。

### 厨房实测

UE 5.9 Preview CL 60351404，Windows Development，Core Ultra 5 225F、RTX 5060，
1280 × 720，D3D12/SM6，屏幕百分比 100、VSync 关、帧率不限。参与对照的每个进程使
用独立用户目录，原有编辑器保持打开。A、B、B、A 表示同一个案例依次启动四个进程。
表中的范围是各组两次运行各自的 p95，单位为 ms。

| 关卡与测试条件 | A 帧时间 / GPU | B 帧时间 / GPU |
| --- | --- | --- |
| 精装图整圈，A 显示全部植物，B 仅隐藏树冠、罗勒和马郁兰三组 | 11.21–14.11 / 8.92–11.64 | 16.01–17.17 / 9.10–11.54 |
| LOD 对照图整圈，A 强制 LOD0，B 强制 LOD1 | 15.16–15.55 / 11.69–11.75 | 15.19–15.60 / 11.59–11.67 |
| 同一水槽相机固定 7 秒，A 强制 LOD0，B 强制 LOD1 | 14.56–14.58 / 10.67–10.69 | 14.06–14.07 / 10.52–10.54 |

八个行走进程均通过原角色的路线与柜体碰撞检查并正常退出 0。预热后按入口返回事件截
取完整计时圈，每圈 939–1,080 帧。LOD 对照图沿用精装图，只替换三份植物网格。烹饪
后三组 LOD0 合计 101,944 个三角形，LOD1 为 32,622，减少约 68%。材质槽保持一致，
三份网格均未使用 Nanite。该构建的静态网格组件强制值 `1`、`2` 分别对应 LOD0、
LOD1。按组件 ID 在实际玩家视图的渲染线程读取 `Proxy->GetLOD(&View)` 和首个已驻留
LOD，四个行走进程对每组各采集 53–54 次，结果与要求的级别一致。判断是否提交了具体
绘制指令或遮挡剔除仍需 GPU frame capture。

固定机位另用四个进程预试。首次采集期间出现 21 个新 PSO、最长帧达 353 ms，因此重
新做了完整 ABBA。表中固定机位四次均为相同位置、姿态、画幅，均已恢复玩家视角并正
常退出。三个正式对照的计时段都没有新增 PSO 日志。这个角度的 GPU p95 下降约 0.15
ms，整圈总帧 p95 两组交叠。若要给其他机器或分辨率设置自动 LOD 阈值，仍需按目标相
机的切换距离、画面差异与性能预算验证。
